# 법숲 — 벡터 DB · LangChain 비교 실험 (2026-10-14)

> 질문: "벡터 DB 를 쓰면, LangChain 을 쓰면 더 나은가?" — 같은 평가 하네스(질문 126개, dev 95 / test 31, 정답 = 근거 조문)로 직접 재서 결정한다.
> 공통 조건: 같은 청크 2,551개 · 같은 bge-m3 벡터 · 같은 질의 재작성(캐시) · 같은 BM25(문자 bigram) + RRF. 설정 결정은 dev 기준(test 는 확인용).

## A. 벡터 DB — 메모리 전수 스캔(현재) vs Qdrant vs pgvector

스크립트 `eval/exp_vectordb.mjs` · 결과 `eval/results/exp_vectordb.json`

| 임베딩 검색 백엔드 | dev hit@5 / MRR | test hit@5 / rec@10 / MRR | 임베딩 검색 p50 | 용량 |
|---|---|---|---|---|
| 메모리 전수 스캔(현재) | 0.937 / 0.759 | 0.903 / 0.935 / 0.757 | 1.9~4.8ms | 행렬 10MB(프로세스 안) |
| Qdrant HNSW(m16, ef128) | 0.937 / 0.759 | 0.903 / 0.935 / 0.757 | 1.3ms(+HTTP) | 컨테이너 224MiB |
| Qdrant 정확 검색 | 같음 | 같음 | 2.3ms | 〃 |
| pgvector HNSW | 0.937 / 0.759 | 0.903 / 0.935 / 0.757 | 4.0ms | 테이블+인덱스 34MB · 컨테이너 80MiB |
| pgvector 정확 검색 | 같음 | 같음 | 3.9ms | 〃 |

- **품질은 다섯 가지가 완전히 같다.** HNSW 상위 10개가 정확 검색 상위 10개와 100% 겹침 — 이 규모에서는 근사 오차가 없다.
- **지연 차이는 몇 ms** — 질의 임베딩(약 0.3초) · LLM(2~4초)에 묻힌다. 대신 DB 는 서비스가 하나 늘고 메모리를 8~22배 더 쓴다. Qdrant 적재 · 색인 62초, pgvector 1.7초.
- **법령 메타데이터 필터**(재작성이 고른 법령으로 걸러 한 번 더 검색해 RRF 에 합침): test MRR 0.757 → 0.783 이지만 dev hit@5 0.937 → 0.926(1문항 하락) — dev 기준으로 채택하지 않음. 필터 자체는 메모리 스캔에서도 같은 결과로 구현된다(DB 고유 이점이 아님).

## B1. LangChain 표준 검색 부품

스크립트 `exp-lc/retrieval.mjs` · 결과 `eval/results/exp_langchain_retrieval.json`

| 시스템 | dev hit@5 / MRR | test hit@5 / rec@10 / MRR | 질의당 p50 |
|---|---|---|---|
| 우리 BM25(문자 bigram) | 0.863 / 0.740 | 0.903 / 0.919 / 0.703 | 3.8ms |
| LangChain BM25Retriever(기본) | 0.884 / 0.688 | 0.935 / 0.925 / 0.653 | 41.3ms |
| LangChain BM25Retriever + 우리 bigram 토크나이저 | 0.821 / 0.651 | 0.903 / 0.973 / 0.673 | 86.4ms |
| 우리 dense / LangChain MemoryVectorStore | 0.863 / 0.702(같음) | 0.839 / 0.903 / 0.735(같음) | 2ms |
| **우리 하이브리드 RRF 1:1(서비스)** | **0.937 / 0.759** | 0.903 / 0.935 / **0.757** | 6.0ms |
| LangChain EnsembleRetriever(BM25 기본 + 벡터) | 0.926 / 0.749 | **0.935** / 0.952 / 0.710 | 44.6ms |

- 예상과 달리 LangChain 기본 BM25(띄어쓰기 토큰 · 부분 문자열 매칭)가 한국어에서 망가지지 않았다 — **질의 재작성이 조사 없는 법령 용어를 만들어 주기 때문**. 하지만 순위 품질(MRR)이 낮고(dev 0.740 → 0.688), 질의마다 전체 문서를 다시 훑어 **7~14배 느리다**. 문서 길이를 `/\w+/` 로 세서 한글 단어가 길이에 안 잡히는 점도 확인.
- 하이브리드끼리는 dev(결정 기준)에서 우리 쪽이 hit@5 · MRR 모두 약간 높고, test 는 hit@5 는 LangChain(+1문항), MRR 은 우리 쪽이 높다 — **바꿀 근거 없음**.

## A2. 규모가 커지면 언제 벡터 DB 가 이기나

스크립트 `eval/exp_scale.mjs` · 결과 `eval/results/exp_scale.json` — 실제 청크에 "방해 벡터"(실제 벡터 + 잡음 후 정규화)를 붙여 늘렸다. 질문 126개의 임베딩 검색 상위 10개 기준.

| 규모 | 청크 | 행렬 | 메모리 스캔 p50 | Qdrant HNSW p50 | HNSW 정확도(정확 검색 top-10 겹침) | Qdrant 적재+색인 |
|---|---|---|---|---|---|---|
| 1배(현재) | 2,551 | 10MB | **1.9ms** | 2.9ms | 100% | 2초 |
| 10배 | 25,510 | 100MB | 19ms | **2.4ms** | 100% | 10초 |
| 40배 | 102,040 | 399MB | 71ms | **3.2ms** | 99.9% | 30초 |
| 100배 | 255,100 | 997MB | 181ms | **3.1ms** | 95.3% | 81초 |

- 스캔은 규모에 **정비례**(10배마다 약 10배), HNSW 는 규모와 거의 무관하게 3ms 안팎 → **역전 지점은 지금의 약 10배(2만 5천 청크)**.
- 100배에서 HNSW 정확도가 95% 로 떨어진다(방해 벡터가 실제와 매우 비슷한 어려운 조건). 규모가 커지면 ef · m 을 평가 하네스로 다시 재야 한다.
- 결론: 법령 15개(현재)는 메모리 스캔이 맞고, 판례 · 해석례까지 넣어 **청크가 수만 개를 넘거나, 개정 조문만 갱신 · 법령별 필터 · 여러 서버 공유가 필요해지면** 벡터 DB 로 옮긴다. `search()` 가 경계라 교체 범위는 `src/index.mjs` 한 곳.

## B2. LangGraph 에이전트형 RAG — 항상 점검 vs 필요할 때만(적응형) vs 한 번 검색(기존)

스크립트 `exp-lc/agent_eval.mjs` · 결과 `eval/results/exp_agent*.json` — test 31문항 + 범위 밖 10문항, 같은 답변 프롬프트 · 같은 채점관(answer_eval 과 같은 기준), 답변 모델 sonnet. LangGraph 는 흐름(상태 · 분기 · 반복)만 맡고 LLM 호출은 기존 `claude -p` 래퍼.

| 시스템 | 정확성 | 충실성 | 정답 조문 인용 | 범위 밖 거절 | LLM 호출(범위 안 / 밖) | 지연 p50 / p90 |
|---|---|---|---|---|---|---|
| 한 번 검색(기존) 1회차 | 29/31 | 31/31 | 28/31 | 10/10 | 1.00 / 1.00 | 4.2s / 5.4s |
| 한 번 검색(기존) 2회차 | 28/31 | 31/31 | 28/31 | 10/10 | 1.00 / 1.00 | 4.2s / 5.6s |
| 에이전트(항상 근거 점검, 최대 2번 재검색) | 29/31 | 29/31 | 30/31 | 10/10 | 2.16 / 2.70 | 6.4s / 9.7s |
| 적응형 v1(근거 없음일 때만, 최대 2번) | 29/31 | 31/31 | 29/31 | 10/10 | 1.19 / **4.10** | 4.3s / 6.5s |
| **적응형 v2(+범위 밖 판정, 재검색 1번) — 채택** | **30/31** | 29/31 | **30/31** | 10/10 | **1.19** / 2.60 | 4.5s / 6.1s |

- **측정 흔들림부터 쟀다**: 같은 기존 시스템을 두 번 돌리니 정확성이 29 → 28(±1). 31문항에서 1~2문항 차이는 잡음일 수 있어, 숫자와 함께 **어떤 문항이 왜 바뀌었나**를 봤다.
- 기존 방식이 틀린 ef-09(결제대행사 · 선불카드) · mj-05(동시이행)는 둘 다 **검색이 정답 조문을 못 가져와 "근거 없음"으로 답한** 경우. 항상 점검하는 에이전트는 이를 고쳤지만 모든 질문에 호출 2배 · 지연 1.5배를 냈다.
- 적응형 v1 은 범위 밖 질문(세금 등)도 "근거 없음"이라 재검색 루프에 들어가 호출 4.1회 → 점검 스키마에 `out_of_scope` 를 두고 재검색을 1번으로 제한(v2).
- v2 는 재검색이 3문항(ef-09 · mj-05 · sb-06)에서만 일어났고 ef-09 · mj-05 를 정답으로 바꿨다. 충실성 감점 2건(cr-11 · sb-03)은 재검색이 없었던, 기존과 같은 경로의 문항 — 생성 · 채점 흔들림으로 판단(기존도 회차마다 다른 문항이 흔들림).
- 한계: 31문항 · 회차당 1번, 채점관이 같은 계열 모델. sb-06(구독 해지 방법 제한)은 세 방식 모두 실패 — 정답 조문(전자상거래법 제21조의2)이 검색 상위에 안 올라오는 문제로 남김.

## 결정 (서비스 적용 2026-10-14)

1. **검색 저장소: 메모리 전수 스캔 유지.** 품질 동일 · 지연 차이 몇 ms · DB 는 메모리 8~22배와 서비스 하나를 더 요구. **청크 약 2만 5천 개(현재의 10배)** 를 넘거나 증분 갱신 · 법령별 필터 · 다중 서버 공유가 필요해지면 Qdrant(또는 pgvector)로 옮긴다 — 실험 A2 의 역전 지점.
2. **검색 부품: 직접 구현 유지.** LangChain 표준 BM25 · Ensemble 은 dev 기준 순위 품질이 낮고 7~14배 느리다.
3. **답변 흐름: LangGraph 적응형(v2) 채택** — `src/agent.mjs`. 평소엔 한 번 검색(LLM 1회), 답이 "근거 없음"일 때만 근거 점검 → 범위 밖이면 그대로 거절, 정보가 빠졌으면 한 번 더 찾아 다시 답한다. 화면에 "근거 점검: 한 번 더 찾았습니다"와 LLM 호출 수를 표시.
